# iOS 免越狱运行时观测:一个 dylib 插件的实现拆解

这篇文章拆解一个注入式 iOS 分析插件的内部实现。它以一个 dylib 的形式被重签进目标 App,在进程内拦截加密调用、文件与系统行为,把抓到的明文/密钥/参数汇聚到一个内置的 HTTP 控制台里查看,并支持运行时砸壳 dump。全程不依赖越狱。

下面按"注入 → 装钩 → 抓取 → 呈现"的数据流走一遍,重点讲机制的来龙去脉,并贴出关键代码。

---

## 一、约束决定架构:为什么是 fishhook + swizzle

先说清楚这套设计是被什么约束逼出来的。

免越狱侧载有一条铁律:**进程拿不到 `dynamic-codesigning`(JIT)entitlement,内核会拒绝任何 RWX / 可执行内存的分配**。这一条直接枪毙了所有需要"运行时生成机器码再执行"的方案——DBI 框架(QBDI 之类)、inline hook 改写指令、trampoline 生成,全部出局。

能用的只剩两类**不产生新代码、只改指针**的技术:

| 目标 | 技术 | 原理 |
|------|------|------|
| C 函数(`CC_MD5`、`open`、`ptrace`…) | **fishhook** | 改写 Mach-O 的**惰性/非惰性符号指针表**,把导入符号的指针换成自己的函数 |
| ObjC 方法(`-canOpenURL:`…) | **method swizzle** | 改写 ObjC runtime 的方法列表 IMP |

两者都只是"把一个指针从 A 改成 B",不触碰代码页权限,因此在非越狱环境里合法可行。整个插件的能力边界由此定死:**能观测 API 边界上的一切,触不到函数内部的指令**。

注入侧走重签名路线,不落地任何越狱依赖:

```sh
# scripts/inject.sh
insert_dylib --strip-codesig --inplace \
    "@executable_path/decrypt_helper.dylib" "$APP_BIN"
```

`insert_dylib` 往主二进制的 load command 里插一条 `LC_LOAD_DYLIB`,`--strip-codesig` 去掉原签名,之后整包重签。App 启动时 dyld 会像加载任何依赖库一样把这个 dylib 拉起来,触发它的 constructor。

## 二、入口:constructor 里的启动顺序学问

dylib 的一切从 `__attribute__((constructor))` 开始。这个函数的**语句顺序本身就是设计**——因为一旦装上 hook,后续任何一次 `open`/`dlopen` 都可能反弹回自己的 hook 里,所以"预热"必须在装钩之前完成。

```objc
// src/core/main.m
__attribute__((constructor))
static void dh_bootstrap(void) {
    // 预热 Foundation 的 locale / NSDateFormatter / backtrace,
    // 避免 hook 安装后首次时间格式化在 hooked_open 内部触发 open/dlopen 递归
    (void)DHTimestampNow();
    (void)DHCallStackFiltered();

    // 诊断落盘目录 + 捕获配置,都在装 hook 前就绪
    NSString *docsDir = [NSSearchPathForDirectoriesInDomains(
        NSDocumentDirectory, NSUserDomainMask, YES) firstObject];
    dh_diag_set_dir(docsDir.fileSystemRepresentation);
    dh_capture_load([docsDir stringByAppendingPathComponent:@".dh_capture.conf"].fileSystemRepresentation);
    dh_noise_load([docsDir stringByAppendingPathComponent:@".dh_noise.conf"]);
    dh_spoof_load([docsDir stringByAppendingPathComponent:@".dh_spoof.conf"]);

    // 安装 hook —— 尽早完成,否则早期发生的加解密会漏抓
    dh_install_all_hooks();

    // HTTP 服务不依赖 UIApplication,可以立刻起
    dh_http_start();

#if __has_include(<UIKit/UIKit.h>)
    // UI 必须等 UIApplication 实例化后再做
    [[NSNotificationCenter defaultCenter]
        addObserverForName:UIApplicationDidFinishLaunchingNotification
        object:nil queue:nil usingBlock:^(NSNotification *_) {
            dh_ui_install_floating();
        }];
#endif
}
```

三个时序要点:

1. **预热先行**。`DHTimestampNow()` 会初始化 `NSDateFormatter` 的 locale,`DHCallStackFiltered()` 会触发 `backtrace` 相关的 dlopen。这些懒加载如果留到 hook 装好之后第一次记录日志时才发生,就会在 `hooked_open` 内部再次调用 `open`,形成递归。提前跑一遍把懒加载状态锁死。
2. **配置比 hook 先加载**。开关、噪声规则、改机配置都持久化在沙箱的 `.dh_*.conf` 里,必须在装钩前就位,否则第一批事件会用默认配置抓取。
3. **UI 后置**。HTTP 服务无依赖可立即启动;悬浮窗依赖 `UIApplication` 实例,挂到 `didFinishLaunching` 通知里延迟创建。

`main.m` 顶部用 `extern` 声明了全部 12 个安装函数,`dh_install_all_hooks()` 顺序调用,覆盖 digest / hmac / 对称 / 非对称 / kdf / evp / file / system / keychain / env / spoof_objc / dyld 十二类。

## 三、抓取管线:C ABI 与 ObjC 的桥接

hook 大量是纯 C 函数(CommonCrypto、libSystem),但日志中心 `DHLogStore` 是 ObjC。中间用一层极薄的 C-to-ObjC 桥打通,让纯 C 的 hook 也能落 ObjC 日志。

```c
// src/core/dh_capture.c
// 由 log_store.m 提供 (ObjC 侧实现)
extern void dh_capture_bridge(int kind, const char *algo,
    const uint8_t *key, size_t key_len,
    const uint8_t *iv,  size_t iv_len,
    const uint8_t *in,  size_t in_len,
    const uint8_t *out, size_t out_len);

void dh_capture_event(dh_event_kind kind, const char *algo,
    const uint8_t *key, size_t key_len,
    const uint8_t *iv,  size_t iv_len,
    const uint8_t *in,  size_t in_len,
    const uint8_t *out, size_t out_len) {
    dh_capture_bridge(kind, algo, key, key_len, iv, iv_len, in, in_len, out, out_len);
}
```

统一入口的签名是精心设计的——`(kind, algo, key, iv, in, out)` 六元组能覆盖所有加密原语:摘要只用 `in/out`,对称加密用满 `key/iv/in/out`,HMAC 用 `key/in/out`,KDF 用 `key(=password)/iv(=salt)/out`。所有 hook 抓到数据后调 `dh_capture_event`,十六进制编码、时间戳、调用栈过滤都在 ObjC 侧统一完成,C 侧只负责搬运。

`DHLogEntry` 是落地的数据结构,字段直接映射上面的六元组:

```objc
// src/core/log_store.h
@interface DHLogEntry : NSObject
@property (nonatomic, assign) DHCategory category;
@property (nonatomic, copy)   NSString *algorithm;   // "AES-128-CBC" / "HMAC-SHA256"
@property (nonatomic, copy)   NSString *operation;   // "encrypt" / "decrypt" / "sign"
@property (nonatomic, copy, nullable) NSData *key;
@property (nonatomic, copy, nullable) NSData *iv;
@property (nonatomic, copy, nullable) NSData *input;
@property (nonatomic, copy, nullable) NSData *output;
@property (nonatomic, copy)   NSString *callStack;   // 已过滤系统/自身的调用栈
@property (nonatomic, assign) uint64_t seq;
@end
```

## 四、重入守卫:hook 自己不能钩死自己

这是注入式插件最容易翻车的地方,值得单独讲。

场景:`hooked_open` 被调用后要记一条日志,记日志要格式化时间、要取调用栈、可能要写文件——这些操作内部又会调 `open`/`stat`/`dlopen`,而这些函数**已经被自己 hook 了**。不加保护就是无限递归直接爆栈。

解法是双保险:

1. **线程局部的重入标志 `dh_in_hook`**。进入 hook 逻辑先置位,走原函数前后清位;记日志这段代码检查到标志已置位就直接跳过记录、只调原函数。这样"hook 内部触发的系统调用"不会被二次记录。
2. **constructor 阶段的预热**(见上一节),把懒加载踢到装钩之前,消掉一部分递归源头。

锁的选型也讲究:`DHLogStore` 的写入路径用 `NSRecursiveLock` 而非普通 `NSLock`。因为同一线程在持锁记录日志时,可能因为某些回调再次进入日志写入路径,普通锁会自己把自己锁死。此前一次改机配置保存的死锁,根因正是"持锁 → 触发 hook → 再次请求同一把锁",最终靠 `NSRecursiveLock + dh_in_hook 守卫` 双管解决。

调用栈也不是原样落库,而是过滤后的:`DHCallStackFiltered()` 从 `backtrace_symbols` 结果里剔除系统库帧和插件自身的帧,只留 App 自己的调用链——这样导出的调用栈直接指向业务代码,不被 runtime 噪声淹没。

## 五、亮点:运行时枚举"哪些符号可以被 rebind"

fishhook 能 rebind 的,只有目标 image **导入表里的 undefined external 符号**。要给用户一个"这个 App 到底有哪些 C 导入可以钩"的清单,就得在运行时自己解析 Mach-O 的符号表。这是插件里技术密度最高的一段,完整贴出来讲。

核心是把**文件偏移**换算成**进程内地址**。Mach-O 的 `LC_SYMTAB` 给出的 `symoff`/`stroff` 是相对文件的偏移,但运行时符号表在内存里,要通过 `__LINKEDIT` 段做换算:

```
linkedit_base = slide + __LINKEDIT.vmaddr - __LINKEDIT.fileoff
symtab = linkedit_base + symoff
strtab = linkedit_base + stroff
```

这与 fishhook 内部定位符号表的算法完全一致,所以"这里枚举得到的导入符号"精确等于"fishhook 能 rebind 的集合"。

遍历 load command 找 `LC_SYMTAB` 和 `__LINKEDIT`,每一步都带边界校验:

```c
// src/core/dh_symtab.c
const uint8_t *cmds = (const uint8_t *)mh + sizeof(struct mach_header_64);
const uint8_t *end  = cmds + mh->sizeofcmds;   // 加载命令区上界, 防越界遍历
const uint8_t *p = cmds;
for (uint32_t i = 0; i < mh->ncmds; i++) {
    if (p + sizeof(struct load_command) > end) break;
    const struct load_command *lc = (const struct load_command *)p;
    if (lc->cmdsize < sizeof(struct load_command)) break;   // 含 cmdsize==0: 防死循环/越界
    if (p + lc->cmdsize > end) break;
    if (lc->cmd == LC_SYMTAB) {
        sym = (const struct symtab_command *)lc;
    } else if (lc->cmd == LC_SEGMENT_64) {
        const struct segment_command_64 *sg = (const struct segment_command_64 *)lc;
        if (strcmp(sg->segname, "__LINKEDIT") == 0) linkedit = sg;
    }
    p += lc->cmdsize;
}
```

拿到 `symoff/stroff` 后不能直接信任——这些字段来自文件,损坏或恶意构造会让后续裸内存读越界。所以在换算地址前,先断言符号表和字符串表**整体落在 `__LINKEDIT` 的文件范围内**:

```c
// symtab/strtab 必须整体落在 __LINKEDIT 的文件范围内, 否则按损坏处理放弃该 image
uint64_t le_lo = linkedit->fileoff, le_hi = (uint64_t)linkedit->fileoff + linkedit->filesize;
uint64_t sym_hi = (uint64_t)sym->symoff + (uint64_t)sym->nsyms * sizeof(struct nlist_64);
uint64_t str_hi = (uint64_t)sym->stroff + (uint64_t)sym->strsize;
if (sym->symoff < le_lo || sym_hi > le_hi) return 0;
if (sym->stroff < le_lo || str_hi > le_hi) return 0;

uintptr_t base = (uintptr_t)slide + (uintptr_t)linkedit->vmaddr - (uintptr_t)linkedit->fileoff;
*symsOut = (const struct nlist_64 *)(base + sym->symoff);
*strOut  = (const char *)(base + sym->stroff);
```

注意 `sym_hi` 的计算用 `(uint64_t)` 提升后再乘 `sizeof(nlist_64)`,避免 `nsyms * 16` 在 32 位里溢出成小值绕过校验——这类"先提升再算,用算出来的上界反查"是解析不可信二进制的标准防御姿势。

判定一个符号是不是"导入",要同时满足三个 `n_type` 位条件:

```c
// src/core/dh_symtab.c
static int undef_name(const struct nlist_64 *s, const char *strtab,
                      uint32_t strsize, const char **nameOut) {
    if (s->n_type & N_STAB) return 0;                 // 调试符号,跳过
    if (!(s->n_type & N_EXT)) return 0;               // 导入必为 external
    if ((s->n_type & N_TYPE) != N_UNDF) return 0;     // 只要未定义(导入)
    uint32_t strx = s->n_un.n_strx;
    if (strx == 0 || strx >= strsize) return 0;       // 字符串索引越界防护
    const char *nm = strtab + strx;
    if (!nm[0]) return 0;
    if (nm[0] == '_') nm++;                            // 去前导下划线 = fishhook 用的名字
    if (!nm[0]) return 0;
    *nameOut = nm;
    return 1;
}
```

最后一步 `if (nm[0] == '_') nm++` 是个容易忽略的细节:C 符号在 Mach-O 符号表里带前导下划线(`_CC_MD5`),而 fishhook 的 `rebind_symbols` 接受的是不带下划线的名字(`CC_MD5`)。这里去掉下划线,枚举出的名字才能直接喂给 fishhook。

对外接口就是带子串过滤和数量上限的回调遍历:

```c
int dh_symtab_imports(int idx, const char *q, int limit, dh_sym_cb cb, void *ctx) {
    const struct nlist_64 *st = NULL; const char *str = NULL;
    uint32_t nsyms = 0, strsize = 0;
    if (!image_symtab(idx, &st, &str, &nsyms, &strsize, NULL)) return 0;
    int matched = 0, called = 0;
    for (uint32_t i = 0; i < nsyms; i++) {
        const char *nm = NULL;
        if (!undef_name(&st[i], str, strsize, &nm)) continue;
        if (q && q[0] && !strstr(nm, q)) continue;      // 子串过滤
        matched++;
        if (cb && (limit <= 0 || called < limit)) { cb(nm, ctx); called++; }
    }
    return matched;
}
```

这段代码不砸壳、不解密,纯读运行时已映射的 metadata,就能列出目标 App 每个 image 的可 rebind 导入符号。它既是"装钩前的侦察工具",本身也是一段可复用的 Mach-O 解析范例。

## 六、加密 hook 的抓法:抓完整的密码学上下文

加密类 hook 分了六个文件,按原语归类:digest / hmac / 对称 / 非对称 / kdf / evp。它们的共同套路是:保存原函数指针 → 用 fishhook 替换 → 在替换函数里先抓上下文再放行。

覆盖面(从符号表确认的实际 rebind 清单)相当完整:

- **CommonCrypto 摘要**:`CC_MD2/4/5`、`CC_SHA1/224/256/384/512` 及各自的 `_Init/_Update/_Final` 流式三段
- **对称**:`CCCrypt`、`CCCryptorCreate(WithMode)`、`CCCryptorUpdate/Final`
- **HMAC**:`CCHmac`、`CCHmacInit/Update/Final`
- **KDF**:`CCKeyDerivationPBKDF`
- **非对称**:`SecKeyCreateSignature/VerifySignature`、`SecKeyCreateEncryptedData/DecryptedData`
- **OpenSSL/BoringSSL EVP**:`EVP_EncryptInit_ex(2)`、`EVP_EncryptUpdate`、`EVP_DecryptInit/Update/Final`、`EVP_CipherInit/Update`、`EVP_CIPHER_CTX_ctrl`

对称加密的抓取要点在于:一次 `CCCrypt` 调用同时拿得到 `key`、`iv`、明文 `dataIn`、密文 `dataOut`,算法/模式/密钥长度从 `CCAlgorithm`、`CCOptions`、`keyLength` 反推。抓到的这组数据凑齐了复现一次加解密的全部要素,这正是"解密助手"的意义——不是逆算法,而是**在算法执行的现场把明文和密钥一起截下来**。

EVP 这条线特别值得抓,因为大量 App 把加密逻辑放在自带的 BoringSSL 里绕开系统 CommonCrypto。EVP 的 `EVP_CipherInit_ex` 在初始化时就把 key/iv 摊在参数里,`EVP_CipherUpdate` 每块吐出密文,顺着这两个点就能还原整个流式加密过程。这些符号往往不在主二进制、而在 App 内嵌的 `*.framework` 里,靠上一节的符号表枚举先定位到哪个 image 导出了它们,再决定对哪个 image 下钩。

## 七、系统行为观测与"改机 / 反检测"

behavior 那一批 hook 覆盖文件、系统调用、Keychain、环境探测:

- **文件**:`open/read/write/mmap/rename/unlink` —— 看 App 读写了哪些沙盒路径、内容是什么
- **反调试/越狱探测**:`ptrace`、`sysctl/sysctlbyname`、`csops`、`stat/lstat/access/faccessat` —— 这些是 App 检测调试器和越狱环境的常用探针
- **Keychain**:`SecItemAdd/CopyMatching/Update/Delete` —— 抓 Keychain 里存取的账号/服务/数据
- **动态库**:`dlopen/dlsym/dladdr`、`_dyld_get_image_name` —— 观测运行时符号解析,同时用来隐藏自身注入痕迹

这里有个双重角色:同一个探针点既能**观测**(记录 App 调了 `ptrace(PT_DENY_ATTACH)`),也能**干预**(让 `sysctl` 查进程状态时返回"未被调试")。改机能力也是同理——`uname`、`sysctlbyname("hw.model")` 这些设备指纹点被 hook 后可返回伪造值,配合持久化的 `.dh_spoof.conf` 实现"一键随机设备"。

`dlsym` 这条线有个额外的意义:有些 App 不直接导入函数,而是运行时 `dlsym` 拿地址再调用,绕过了导入表(fishhook 就钩不到)。对 `dlsym` 本身下钩,就能在 App 查询符号时把返回地址重定向到自己的实现,补上 fishhook 的盲区。

隐藏自身也靠这批 hook:枚举 image 时把自己的 dylib 从 `_dyld_get_image_name` 结果里抹掉,`canOpenURL:` 探测自己注册的 URL scheme 时返回否——避免被 App 的完整性检测发现多了一个模块。

## 八、运行时砸壳:把解密后的 __TEXT dump 出来

App Store 的二进制 `__TEXT` 段被 FairPlay 加密,静态拿不到明文代码。但运行时它必然被 dyld 解密后映射进内存——砸壳就是**在进程内把已解密的内存段按 Mach-O 结构重新拼回一个可分析的文件**。

流程:遍历 `_dyld` image 找到目标 → 读它的 `mach_header` 和 load command → 对每个 `LC_SEGMENT_64` 按 `vmaddr+slide` 定位内存、按 `filesize` dump → 把 `LC_ENCRYPTION_INFO_64` 的 `cryptid` 改成 0(标记为已解密)→ 写盘。产物通过内置 HTTP 服务的下载端点取走。`dump_manager` 管理任务状态(进行中/完成/产物路径),`macho_dump` 做实际的段拷贝和头部改写。

这和第五节的符号表解析共用同一套 Mach-O 遍历基建,边界校验的严谨程度也一致——dump 面对的是运行时内存,任何一个被信任的越界字段都会导致段错误。

## 九、控制台:进程内的本地 HTTP 服务

呈现层没有走系统 UI 的重活,而是在进程里起了个本地 HTTP 服务(`http_server.m`,约 1000 行),配一个内联到 `web_index_html.h` 的单页前端。所有能力以 `/api/*` 的 JSON 端点暴露:

- `/api/stats`、`/api/logs`、`/api/detail` —— 统计、日志列表、单条明细(key/iv/明文/密文的 hex 与 UTF-8 视图)
- `/api/pause` —— 全局或按分类暂停记录(高频的文件类可单独停掉,不影响加密类继续抓)
- `/api/config` —— 每类内存保留条数、单文件滚动上限,持久化在 `.dh_logcfg.conf`
- `/api/spoof` —— 改机/越狱绕过配置的增删
- `/api/dump` —— 触发砸壳、查询进度、下载产物
- 沙盒文件浏览:列目录、文本/Hex 预览、下载,路径经 `dh_files_resolve_file` 归一化后校验必须落在允许范围内,防目录穿越

日志系统还有几个工程化的点:**分类桶**(加密/文件/系统各自独立,清理和暂停互不影响)、**噪点桶**(与已知特征串完全相等的高频日志改投噪声桶,不污染主事件流但仍照常落盘)、**落盘滚动**(单文件超限滚为 `.1/.2/.3`,最多 3 个备份)。这些都是为了在高频调用下让主事件流保持可读。

悬浮窗严格只显示统计数字、Web 地址和基础操作,不显示日志正文；检索、详情、导出和配置统一在 Web 控制台完成。这是刻意的信息分层,避免敏感明文在 App 界面上被旁观者瞥见。

## 十、整体数据流回顾

把十节串起来,一次加密调用的完整生命周期是这样的:

```
App 调 CCCrypt(...)
   │  (fishhook 已把导入表指针改到 hooked_CCCrypt)
   ▼
hooked_CCCrypt: 置 dh_in_hook → 抓 key/iv/in/out
   │
   ▼
dh_capture_event(SYMMETRIC, "AES-128-CBC", key, iv, in, out)
   │  (C → ObjC 桥)
   ▼
dh_capture_bridge → DHLogStore append(DHLogEntry)
   │  (NSRecursiveLock 保护, hex 编码, 过滤调用栈, 落盘)
   ▼
清 dh_in_hook → 调原始 CCCrypt 返回 App
   ┊
   ┊  (异步, 另一线程)
浏览器 GET /api/logs → http_server → DHLogStore snapshot → JSON → 前端渲染
```

整套设计的内核,是把"免越狱不能生成代码"这条硬约束,转化成一套纯指针改写 + 运行时 Mach-O 解析的观测体系:fishhook 钩 C 导入、swizzle 钩 ObjC、dlsym 重定向补盲区、符号表枚举做侦察、内存重组做砸壳,最后用一个进程内 HTTP 控制台把这些能力统一呈现。每一处的边界校验和重入守卫,都是"在别人的进程里动手术"这件事逼出来的纪律。

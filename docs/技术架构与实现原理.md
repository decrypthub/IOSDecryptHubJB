# IOSDecryptHub 技术架构与实现原理

> 本文从工程实现角度拆解 IOSDecryptHub 的架构：它如何在**不越狱**的前提下注入目标 App 进程，实时截获加解密、文件、系统、Keychain、动态加载等运行时行为，并通过进程内 HTTP 控制台与 MCP 服务对外暴露分析能力。全文只讲技术原理，不涉及使用教程。

---

## 一、约束反推架构：为什么只能是 fishhook + swizzle

理解这个项目，必须先理解压在它头上的那条内核级硬约束。

免越狱侧载的进程**拿不到 `dynamic-codesigning`（JIT）entitlement**。没有它，内核会拒绝进程分配任何 RWX / 可执行内存。这一条直接判了一整类 hook 技术的死刑：

- inline hook（改写目标函数开头几条指令跳到自己的桩）—— 需要写指令，出局
- trampoline / 运行时生成机器码 —— 需要可执行内存，出局
- DBI 框架（QBDI、Frida Stalker）—— 依赖动态代码生成，出局

剩下能用的，只有**不产生任何新指令、只改指针**的两类技术：

| 拦截目标 | 技术 | 本质 |
|----------|------|------|
| C 函数（`CCCrypt`、`open`、`ptrace`…） | **fishhook** | 改写 Mach-O 导入符号指针表里的函数指针 |
| ObjC 方法（`-canOpenURL:`…） | **method swizzle** | 交换 ObjC runtime 方法列表里的 IMP |

两者都只是"把一个指针从 A 改成 B"，不触碰代码页权限位，因此在非越狱环境合法可行。这条约束也定死了整个平台的**能力边界**：能观测一切跨越 API 边界的数据（参数、返回值、缓冲区），但**永远触不到函数内部的指令流**。项目的全部设计，都是围绕"只能改指针"这个前提展开的。

> 架构铁律（`docs/ARCHITECTURE_BOUNDARY.md`）把这条上升为不可违反的边界：即使在越狱环境已有 RWX 权限，核心引擎仍只用 fishhook + swizzle，绝不引入第二套 hook 实现。越狱框架（ElleKit）**仅作为把 dylib 加载进目标进程的加载器**，其 hook API（`MSHookFunction` / `%hook`）一律禁用。

## 二、双轨注入，一份核心

同样的一份 `src/` 核心 dylib，通过两条完全不同的载体进入目标进程，编译期用 `DH_VARIANT` 宏区分：

```
                   ┌─────────────────────────────┐
  TrollStore 路线 → │                             │
  (patch Mach-O)    │   共享核心 dylib (src/)      │
                    │   fishhook + ObjC swizzle   │
  越狱路线        → │                             │
  (ElleKit 加载)    └─────────────────────────────┘
```

- **TrollStore（免越狱）**：管理器 App 直接 patch 目标 App 的 Mach-O，向 load command 区插入一条 `LC_LOAD_DYLIB`，并把共享 dylib 复制进包，重签后 dyld 会像加载普通依赖库一样把它拉起。patch 逻辑是纯 C 的 `app-trollstore/IOSDecryptHubTS/macho_patch.c`，与核心引擎完全隔离。
- **越狱（rootless）**：ElleKit 加载器读取 plist 偏好，判断当前进程是否是被选中的目标，是则 `dlopen` 主 dylib。加载器是独立薄层，只做"读偏好 → dlopen"，不参与任何 hook。

两条路线的分歧仅在"如何把 dylib 塞进进程"，一旦 dylib 起来，后续的 hook、抓取、呈现走的是同一套代码。这是本项目最重要的架构决策：**一份核心代码，多套注入载体**。

## 三、入口：constructor 里的启动顺序即设计

dylib 被 dyld 加载后，`__attribute__((constructor))` 在 `main()` 之前触发。`src/core/main.m` 的启动顺序**不是随意排列，语句顺序本身就是防御设计**：

```objc
// src/core/main.m — dh_bootstrap()
(void)DHTimestampNow();          // ① 预热时间格式化 (locale/NSDateFormatter)
(void)DHCallStackFiltered();     // ① 预热 backtrace
dh_capture_load(...);            // ② 加载捕获/噪声/改机配置
dh_noise_load(...);
dh_spoof_load(...);
dh_install_all_hooks();          // ③ 一次性装 13 类 hook
dh_http_start();                 // ④ 启动 HTTP + MCP 服务
// ⑤ UIApplicationDidFinishLaunching → dh_ui_install_floating()
```

四个时序要点：

1. **预热必须先于装钩**。`DHTimestampNow()` 会初始化 `NSDateFormatter` 的 locale，`DHCallStackFiltered()` 会触发 backtrace 相关的 dlopen。这些懒加载如果拖到 hook 装好之后第一次记录日志时才发生，就会在 `hooked_open` 内部再次调用 `open`，形成无限递归。提前跑一遍，把懒加载状态锁死在装钩之前。
2. **配置先于 hook**。开关、噪声规则、改机配置持久化在沙箱的 `.dh_*.conf`，必须在装钩前就位，否则第一批事件会用默认配置抓取。
3. **hook 尽早装完**。装晚了，App 早期（甚至 constructor 链上）发生的加解密会漏抓。
4. **UI 后置**。HTTP 服务无依赖可立即起；悬浮窗依赖 `UIApplication` 实例，挂到 `didFinishLaunching` 通知里延迟创建，并额外补一次 `dispatch_after` 兜底（有些 App 加载 dylib 时 `UIApplication` 已存在）。

`dh_install_all_hooks()` 顺序调用 13 个安装函数，覆盖 digest / hmac / 对称 / 非对称 / kdf / evp / file / system / keychain / env / spoof_objc / dyld / network 十三类。

## 四、抓取管线：C ABI 与 ObjC 的桥接

hook 大量是纯 C 函数（CommonCrypto、libSystem），而日志中心 `DHLogStore` 是 ObjC。中间用一层极薄的 C-to-ObjC 桥打通：

```c
// src/core/dh_capture.c
extern void dh_capture_bridge(int kind, const char *algo,
    const uint8_t *key, size_t key_len, const uint8_t *iv, size_t iv_len,
    const uint8_t *in,  size_t in_len,  const uint8_t *out, size_t out_len);
```

统一入口的 `(kind, algo, key, iv, in, out)` 六元组是精心设计的——它能覆盖所有密码学原语：摘要只用 `in/out`，对称加密用满 `key/iv/in/out`，HMAC 用 `key/in/out`，KDF 用 `key(=password)/iv(=salt)/out`。C 侧只负责搬运原始字节，十六进制编码、时间戳、调用栈过滤全部在 ObjC 侧统一完成。

落地的数据结构 `DHLogEntry` 字段直接映射这个六元组：`category / algorithm / operation / key / iv / input / output / callStack / seq`。这套统一 schema 让下游（HTTP JSON、MCP `export_events`）无需为每类原语单独适配。

## 五、重入守卫：hook 不能钩死自己

这是注入式插件最容易翻车的地方，也是"不崩溃原则"最集中的体现。

**问题**：`hooked_open` 被调用后要记一条日志，记日志要格式化时间、取调用栈、可能写文件——这些操作内部又会调 `open` / `stat` / `dlopen` / `write`，而这些函数**已经被自己 hook 了**。不加保护就是无限递归直接爆栈，宿主 App 当场崩溃。

**双保险解法**：

1. **线程局部重入标志 `dh_in_hook`**（`extern __thread int dh_in_hook;`）。进入记录逻辑前置位、走原函数前后复位；每个 hook 一进来先检查 `if (!dh_in_hook && ...)`，标志已置位就直接放行原函数、跳过记录。这样"hook 内部触发的系统调用"不会被二次记录，也不会递归。它是 `__thread` 的——每个线程一份，避免多线程互相踩标志。

```c
// src/hooks/behavior/hook_file.m 里的典型模式
if (!dh_in_hook && fd >= 0 && dh_is_app_file(path)) {
    dh_in_hook = 1;
    file_log(@"open", path, ...);   // 内部的 open/stat 因标志已置位而放行
    dh_in_hook = 0;
}
```

2. **constructor 阶段的预热**（见第三节），把懒加载踢到装钩之前，从源头消掉一部分递归。

**锁的选型也讲究**。`DHLogStore` 的写入路径、`dh_spoof` 的保存路径都用 `NSRecursiveLock` 而非普通 `NSLock`：同一线程持锁记录日志时，可能因回调再次进入同一写入路径，普通锁会自己把自己锁死。项目历史上确实出过一次"持锁 → 触发 hook → 再次请求同一把锁"的死锁，最终靠 `NSRecursiveLock + dh_in_hook 守卫`双管解决。`dh_spoof.m` 的注释写得很直白：`save 时 writeToFile 会触发 stat/access → 回调 should_hide_*，同线程重入`。

**调用栈也不是原样落库**。`DHCallStackFiltered()` 从 `backtrace_symbols` 结果里剔除系统库帧和插件自身的帧，只留 App 自己的调用链——导出的调用栈直接指向业务代码，不被 runtime 噪声淹没。

## 六、运行时符号侦察：枚举"哪些符号可被 rebind"

fishhook 能 rebind 的，只有目标 image **导入表里的 undefined external 符号**。要给用户/AI 一个"这个 App 到底有哪些 C 导入可以钩"的清单，就得在运行时自己解析 Mach-O 的符号表（`src/core/dh_symtab.c`）。

核心是把**文件偏移**换算成**进程内地址**。`LC_SYMTAB` 给出的 `symoff` / `stroff` 是相对文件的偏移，运行时符号表在内存里，要通过 `__LINKEDIT` 段换算：

```
linkedit_base = slide + __LINKEDIT.vmaddr - __LINKEDIT.fileoff
symtab = linkedit_base + symoff
strtab = linkedit_base + stroff
```

这与 fishhook 内部定位符号表的算法完全一致，所以"这里枚举出的导入符号"精确等于"fishhook 能 rebind 的集合"。

解析不可信二进制有几处标准防御姿势：

- **边界校验遍历 load command**：`p + lc->cmdsize > end` 越界即停，`cmdsize < sizeof(load_command)`（含 `cmdsize==0`）即停，防死循环/越界。
- **符号表整体落在 `__LINKEDIT` 范围内才信任**：换算地址前先断言 `sym->symoff >= le_lo && sym_hi <= le_hi`，否则按损坏 image 放弃。`sym_hi` 用 `(uint64_t)nsyms * sizeof(nlist_64)` 先提升再算，避免 32 位乘法溢出绕过校验。
- **导入符号判定三条件**：`!(N_STAB)` 且 `N_EXT` 且 `(N_TYPE)==N_UNDF`，再加字符串索引越界防护。
- **去前导下划线**：`_CC_MD5` → `CC_MD5`，因为 fishhook 的 `rebind_symbols` 接受的是不带下划线的名字。

这段代码不砸壳、不解密，纯读运行时已映射的 metadata，就能列出每个 image 的可 rebind 导入符号。它既是"装钩前的侦察工具"（决定对哪个 image 下钩），本身也是一段可复用的 Mach-O 解析范例。这套 Mach-O 遍历基建在符号枚举、xref 扫描、砸壳三处复用。

## 七、加密 hook：在算法执行现场截下明文与密钥

加密类 hook 按原语分六个文件：digest / hmac / 对称 / 非对称 / kdf / evp。共同套路是 **保存原函数指针 → fishhook 替换 → 替换函数里先放行原函数、再抓上下文**。

以 `hook_symmetric.m` 的 `CCCrypt` 为例，一次调用同时拿得到 `key`、`iv`、明文 `dataIn`、密文 `dataOut`，算法/模式/密钥长度从 `CCAlgorithm` / `CCOptions` / `keyLength` 反推：

```objc
// src/hooks/crypto/hook_symmetric.m
CCCryptorStatus s = orig_CCCrypt(op, alg, options, key, keyLength, iv, ...);
if (!dh_capture_sub_enabled(DH_CAP_SYMMETRIC)) return s;   // 分类开关早退
DHLogEntry *e = [DHLogEntry new];
e.algorithm = sym_full_name(alg, keyLength, mode, pad);    // "AES-128-CBC-PKCS7"
e.key = [NSData dataWithBytes:key length:keyLength];
e.iv  = (iv && mode != kCCModeECB) ? [NSData dataWithBytes:iv length:ivLen] : nil;
e.input  = [NSData dataWithBytes:dataIn  length:dataInLength];
e.output = [NSData dataWithBytes:dataOut length:*dataOutMoved];
[[DHLogStore shared] append:e];
```

这就是"解密助手"的技术内核：**不是去逆算法，而是在算法执行的现场把明文和密钥一起截下来**。

几个工程细节体现了"运行在别人进程里"的纪律：

- **流式加密用状态机跟踪**。`CCCryptorCreate*` 时用 `NSMapTable` 以 `CCCryptorRef` 为键建一个 `DHCryptorState`，`CCCryptorUpdate` 逐块累积明文/密文，`CCCryptorFinal` 时合并落一条完整日志，`CCCryptorRelease` 清理状态。
- **累积有上限**。整文件流式加解密会把全部明文驻留内存撑爆宿主 OOM，所以累积到 4MB 即停止追加（明文被截断，但换宿主不崩）。
- **fail-loud 自检**。`CCCryptorFinal` 收到从未被 Create hook 记录过的 `cryptorRef`，说明创建函数漏挂了，记一条 `DH_ERR`；装钩后立即检查 `orig` 指针是否仍为 NULL，为 NULL 即 `dh_health_hook_fail`。

覆盖面（从符号表确认的实际 rebind 清单）：CommonCrypto 摘要三段式（`CC_SHA256_Init/Update/Final` 等）、`CCCrypt` / `CCCryptor*`、`CCHmac*`、`CCKeyDerivationPBKDF`、`SecKeyCreateSignature/EncryptedData` 等，以及 **OpenSSL/BoringSSL EVP** 一整条线（`EVP_CipherInit_ex` / `EVP_CipherUpdate` / `EVP_CIPHER_CTX_ctrl`）。EVP 这条线特别关键：大量 App 把加密塞进自带 BoringSSL 绕开系统 CommonCrypto，而这些符号往往不在主二进制、而在内嵌 `*.framework` 里——靠第六节的符号枚举先定位到哪个 image 导出了它们，再决定对哪个 image 下钩。

## 八、行为观测与 dlsym 盲区补偿

behavior 那一批 hook 覆盖文件、系统调用、Keychain、环境探测、动态库、网络：

- **文件**：`open/read/write/mmap/rename/unlink` —— App 读写了哪些沙盒路径、内容是什么
- **反调试/越狱探测**：`ptrace` / `sysctl` / `csops` / `stat/lstat/access` —— App 检测调试器和越狱环境的常用探针
- **Keychain**：`SecItemAdd/CopyMatching/Update/Delete`
- **动态库**：`dlopen/dlsym/dladdr`、`_dyld_get_image_name`

这里有个**双重角色**：同一个探针点既能观测（记录 App 调了 `ptrace(PT_DENY_ATTACH)`），也能干预（让 `sysctl` 查进程状态时返回"未被调试"）。改机同理——`uname`、`sysctlbyname("hw.model")` 等设备指纹点被 hook 后返回伪造值，配合持久化的 `.dh_spoof.conf` 实现设备指纹伪装。

**dlsym 重定向补 fishhook 盲区**是这一节的技术亮点。fishhook 只能改导入表，但有些 App 不直接导入函数，而是运行时 `dlsym(handle, "CCCrypt")` 拿地址再调用——这类调用绕过了导入表，fishhook 钩不到。解法是对 `dlsym` 本身下钩：

```c
// src/core/dh_dlsym_redirect.c
// 每个 crypto/behavior hook 装钩时把 {符号名 → 替换函数} 注册进一张表
void dh_dlsym_register_rebindings(const struct rebinding *r, size_t n);
// hooked_dlsym 查表, 命中就把返回地址重定向到自己的实现
void *dh_dlsym_redirect_lookup(const char *symbol);
```

于是 `hooked_dlsym` 在 App 查询符号时，先查这张表，命中就返回自己的 hook 地址而非真实地址——补上了 fishhook 的运行时解析盲区。

**隐藏自身**也靠这批 hook：枚举 image 时把自己的 dylib 从 `_dyld_get_image_name` 结果里抹掉，`canOpenURL:` 探测自己注册的 URL scheme 时返回否，避免被 App 完整性检测发现多了一个模块。

## 九、运行时砸壳：把解密后的 __TEXT 重组成文件

App Store 二进制的 `__TEXT` 段被 FairPlay 加密，静态拿不到明文代码。但运行时它必然被 dyld 解密后映射进内存——砸壳就是**在进程内把已解密的内存段按 Mach-O 结构重新拼回一个可分析的文件**（`src/core/macho_dump.m` + `dump_manager.m`）：

```
遍历 _dyld image 找到目标
  → 读 mach_header 和 load command
    → 对每个 LC_SEGMENT_64 按 vmaddr+slide 定位内存、按 filesize dump
      → 把 LC_ENCRYPTION_INFO_64 的 cryptid 改成 0 (标记为已解密)
        → 写盘, 经内置 HTTP 下载端点取走
```

这和第六节的符号解析共用同一套 Mach-O 遍历基建，边界校验的严谨程度一致——dump 面对的是运行时内存，任何一个被信任的越界字段都会段错误。砸壳全程在 `dh_in_hook=1` 下执行（大量 open/read/write 不该被自己的 file hook 记录并递归），`dump_manager` 管任务状态（进行中/完成/产物路径）。

## 十、呈现层：进程内 HTTP 控制台 + MCP 服务

呈现层没有走系统 UI 的重活，而是在进程里起了个本地 HTTP 服务（`src/server/http_server.m`），监听 `0.0.0.0:8088`，配一个内联到 `web_index_html.h` 的单页前端。所有能力以 `/api/*` 的 JSON 端点暴露：

- `/api/stats` `/api/logs` `/api/detail` —— 统计、日志列表、单条明细（key/iv/明文/密文的 hex 与 UTF-8 视图）
- `/api/pause` —— 全局或按分类暂停记录（高频文件类可单独停，不影响加密类）
- `/api/config` —— 每类内存保留条数、单文件滚动上限
- `/api/spoof` —— 改机/越狱绕过配置增删
- `/api/dump` —— 触发砸壳、查进度、下载产物
- 沙盒文件浏览 —— 列目录、文本/Hex 预览、下载；路径经 `dh_files_resolve_file` 归一化后必须落在允许范围内，防目录穿越

几个工程化的点：**分类桶**（加密/文件/系统各自独立，清理和暂停互不影响）、**噪点桶**（与已知特征串完全相等的高频日志改投噪声桶，不污染主事件流但仍照常落盘）、**落盘滚动**（单文件超限滚为 `.1/.2/.3`，最多 3 个备份）。悬浮窗刻意只显示统计数字和 Web 地址，不显示日志正文——避免敏感明文在 App 界面上被旁观者瞥见，检索/详情/导出统一在 Web 控制台完成。

### MCP：复用同一端口，暴露逆向工具链

MCP（Model Context Protocol）服务**复用 8088 端口**，端点固定 `POST /api/mcp`，不额外开端口——注入场景下每多开一个端口就多一分被 App 检测的风险。

- **传输**：MCP Streamable HTTP，JSON-RPC 2.0，支持 `initialize` / `tools/list` / `tools/call`。
- **内容协商**：`Accept: text/event-stream` 时以单帧 SSE 返回，否则 `application/json`；`initialize` 应答下发 `Mcp-Session-Id` 会话头。
- **能力**：内嵌 Capstone 5.0.1（仅 ARM/AArch64）做反汇编，配合 `vm_read_overwrite` 安全读进程内存。工具集覆盖 `disassemble` / `analyze_function` / `disassemble_function` / `list_imports` / `get_macho_info` / `find_xrefs` / `find_string_refs` / `find_selector_refs` / `find_function_refs` / `list_functions` / `objc_resolve_imp` / `export_events` 等——从字节反汇编、函数边界（`LC_FUNCTION_STARTS`）、交叉引用扫描到 ObjC runtime 查询一整套逆向能力。
- **不崩溃**：`analyze_function` 读不可读地址时安全返回 `isError:true` 信封而非崩溃，这是把"不崩溃原则"贯彻到工具层。

MCP 加工具有固定的 3 个插入点（`mcp_server.m` 的 handler 实现、`tool_definitions` 数组、`dispatch_tool` 分发链），HTTP 传输与工具逻辑严格分离（`http_server.m` 只管传输，`mcp_server.m` 管方法分发）。

## 十一、PC 端网关 idh：HTTP MCP → stdio MCP 桥接

设备上的 MCP 是 HTTP 传输，但 Codex / Claude 等 AI 客户端主要支持 **stdio MCP**。`idh`（零运行时依赖的 Python 3.10+ CLI）填这个缝：

1. **连接**：`idh connect <设备 IP>:8088` 手动指定设备（无自动发现——注入场景控制不了宿主 `Info.plist`，Bonjour/mDNS 会静默失败），连接保存到 `~/.config/idh/connections.json`。
2. **桥接**：把设备端 Streamable HTTP MCP 转换成本地 stdio MCP，让 AI 客户端一次配置直接使用。

两种网关形态：

- **聚合网关**（`idh mcp`）：同时管理多个已连接 App，暴露固定工具集（`idh_list_devices` / `idh_list_tools` / `idh_get_tool_schema` / `idh_call_tool` / `idh_get_panel_url`），避免设备上下线导致 MCP 客户端缓存动态 `tools/list`。适合让 Agent 自主选目标。
- **透明代理**（`idh mcp --target <id>`）：目标进程启动时固定，把远端工具及完整 schema 原样暴露，调用体验最好。

一个防误操作的设计：透明代理会在**修改型**远端工具的 schema 里注入必填 `allow_mutation` 字段，确认后在本地移除再转发；只读工具（查询/反汇编）不受限。`AppEndpoint` 是 frozen dataclass 不可变，改属性用 `with_properties()` 返回新实例——把不可变性作为路由正确性的保证。

## 十二、一次加密调用的完整生命周期

把各层串起来，一次 `CCCrypt` 调用的完整数据流：

```
App 调 CCCrypt(...)
   │  (fishhook 已把导入表指针改到 hooked_CCCrypt)
   ▼
hooked_CCCrypt: 先调 orig_CCCrypt 放行 → 检查分类开关 → 抓 key/iv/in/out
   │
   ▼
构造 DHLogEntry("AES-128-CBC", key, iv, in, out)
   │  (置 dh_in_hook 防递归)
   ▼
[DHLogStore append:] → NSRecursiveLock 保护 → hex 编码 + 过滤调用栈 + 落盘滚动
   │
   ▼
清 dh_in_hook → 返回 App
   ┊
   ┊  (异步, 另一线程)
浏览器 GET /api/logs ─┐
AI 客户端 POST /api/mcp ┼→ http_server → DHLogStore snapshot → JSON
idh 网关 stdio → HTTP ─┘        MCP 工具 → Capstone / vm_read / Mach-O 解析
```

## 十三、架构内核一句话

整套设计的内核，是把"**免越狱不能生成代码**"这条内核级硬约束，转化成一套**纯指针改写 + 运行时 Mach-O 解析**的观测体系：

- fishhook 钩 C 导入、swizzle 钩 ObjC、dlsym 重定向补运行时解析盲区；
- 符号表枚举做装钩前侦察、内存段重组做砸壳；
- 一份核心 dylib 走 TrollStore / 越狱双轨注入；
- 进程内 HTTP 控制台 + 复用端口的 MCP 服务统一呈现，PC 端 idh 把 HTTP MCP 桥成 stdio 供 AI 客户端消费。

而每一处的边界校验、重入守卫、累积上限、fail-loud 自检，都不是可选的工程洁癖——它们是"**在别人的进程里动手术，一次 crash 就杀死宿主**"这件事逼出来的纪律。

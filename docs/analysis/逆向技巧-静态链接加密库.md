# 逆向技巧：标准加密 hook 全空时，怎么找 key

> 适用场景：目标 App 的网络/文件里能看到密文，但 `sym` / `asym` / `digest` 分类没有对应事件。
> 典型目标：CryptoSwift、静态链接 OpenSSL/BoringSSL、自研分组密码或大数实现。
> 结论先行：不要只盯着加密 API。去找「加密库初始化 key 时调用的标准库函数」，用
> `hook_import(capture_memory)` 在命中瞬间抓缓冲区。

## 1. 先确认「真的没抓到」

1. `get_capture_coverage`：看是哪些层没覆盖，区分「没命中」和「没装 hook」；
2. `query_events(category:"all", query:"CCCrypt")` / `SecKey` / `EVP_`：确认标准加密 API 无事件；
3. `query_events(category:"net")`：网络层已经拿到端点/密文，说明请求确实发出，问题在加密实现内部；
4. 如果 `get_capture_coverage` 的 `blind_spots` 明确写了静态链接/纯 Swift/自研实现，本技巧就是目标路径。

## 2. 判断加密实现是谁

- `list_loaded_images` / `get_macho_info`：看是否加载了 OpenSSL、BoringSSL、CryptoSwift 相关镜像；
  静态链接时可能没有独立镜像，只有主程序。
- `list_imports`：看主程序导入了哪些密码学符号。完全没有 `CCCrypt` / `SecKey*` / `EVP_*`，
  但业务确实在加密，基本可以判定为静态实现。
- `list_functions(query:"...")` / `find_string_refs("CryptoSwift")` / `find_string_refs("AES")`：
  Swift 静态库通常还留有一些字符串/符号线索；strip 后可能只剩 `sub_<addr>`。
- 目标不是逆出完整算法，而是找到「key 进入加密库的第一个可观测点」。

## 3. 找「指针 + 长度」型导入

静态加密库最终仍然要用系统调用/标准库。优先枚举这些候选：

| 候选 | 典型用途 | 抓什么 |
|---|---|---|
| `mlock(ptr, len)` | CryptoSwift 初始化 AES key buffer | key 缓冲区 |
| `memcpy(dst, src, n)` / `memmove` | key/IV/明文拷贝 | 选择持有 key/明文的那一侧指针 |
| `read` / `recv` / `send` / `SSL_write` | 明文进出网络栈 | 请求/响应明文 |
| `getrandom` / `SecRandomCopyBytes` / `arc4random_buf` | key/IV 随机源 | 随机字节 |
| `memset` / `bzero` | key 清除点 | 可反推缓冲区生命周期 |
| `CCCrypt` / `CC_*` / `EVP_*` / `SecKey*` | 动态链接时的常规入口 | 输入/输出 |

用 `list_images` 拿到 `image_index`，再 `list_imports(image_index, query:"mlock")` 确认符号在导入表里。
**不在导入表就不能 fishhook**，这是项目铁律的硬边界，不要试图用 inline hook 绕过。

## 4. 命中瞬间抓内存

关键：`capture_memory` 在 thunk handler 内、原函数返回前拷贝，不是事后 `read_memory`。

```json
{
  "name": "hook_import",
  "arguments": {
    "symbol": "mlock",
    "label": "crypto-key-buffer",
    "capture_memory": { "ptr_arg": 0, "len_arg": 1, "max_bytes": 4096 }
  }
}
```

- `ptr_arg` / `len_arg` 是 x 寄存器索引（0..8），不是参数序号之外的魔法；
- `len_arg: -1` 时用 `max_bytes` 固定长度，适合长度参数不在寄存器的 API；
- `hook_method` 同理：x0=self，x1=_cmd，x2..=方法参数；
- 抓到的内容在事件的 `input` / `inputHex` / `inputUtf8` / `inputDump`。

### 为什么事后回读不行

缓冲区可能在原函数返回后立刻释放/复用。只保存 `x0` 指针 + 事后 `read_memory`，常见结果是零、
堆头或别人的数据。这不是工具缺陷，是生命周期问题；`capture_memory` 解决的正是这个结构性盲区。

## 5. 验证闭环

拿到候选 key 后必须闭环，不能只看「像 key」：

1. 用候选 key 解密网络里的密文，得到结构合理的明文（JSON / Protobuf / 表单）；
2. 用同一 key、同一模式、同一填充回加密，密文与原始数据逐字节一致；
3. 同一进程内多次触发（换 `sessionId` / nonce / 时间戳），观察 key 是否变化：
   - 不变 → 硬编码常量或长生命周期密钥；
   - 每次都变 → 会话密钥/随机密钥，继续找协商或随机源；
4. 静态 dump 里的常量只能作为候选；只有动态捕获 + 回加密闭环才能证明它就是运行时 key。

## 6. 实战：山东航空 CryptoSwift

- 标准 `sym` / `asym` hook 全空，网络 body 是 `{"param": Base64(...)}`；
- `list_imports` 找到 `mlock`，`hook_import` + `capture_memory` 命中 16 字节 ASCII key；
- 同进程三次登录，`sessionId` / `deviceKey` / `timeStamp` 变化但 key 不变 → 硬编码常量；
- AES-128-ECB-PKCS7 解密得到业务 JSON，回加密逐字节一致。

详细记录见 [山东航空-登录加密.md](山东航空-登录加密.md)。

## 7. 什么时候仍然抓不到

- key 完全由静态库内部生成，只在寄存器/栈上短暂存在，且不经过任何导入函数；
- 加密库把 `mlock` / `memcpy` 等全部内联（LTO），导入表里没有可 hook 的点；
- 明文只存在于自研网络栈内部（例如裸 socket + 自带 TLS），而项目禁止 inline hook。

这些情况下：

- 优先找调用层（Swift/ObjC wrapper）用 `hook_method(describe_args:true)`；
- 或找随机源、序列化边界、日志/缓存落盘等旁路；
- 不要为了一个 key 引入 inline hook / trampoline，违反项目架构铁律。

## 8. 一页检查表

- [ ] `get_capture_coverage` 确认 blind spot
- [ ] 网络层已拿到密文和端点
- [ ] `list_images` → `list_imports` 枚举候选符号
- [ ] 优先尝试 `mlock` / `memcpy` / `read` / `send` / `getrandom`
- [ ] `hook_import(capture_memory)` 命中瞬间抓，不事后回读
- [ ] 解密 + 回加密闭环
- [ ] 多次触发确认 key 生命周期
- [ ] 记录到 `docs/analysis/`，脱敏后再提交
